## Candidate: Rule-based + in-browser local model

### Findings
- Transformers.js (Hugging Face's official JS port of `transformers`) runs classification, feature-extraction, translation, summarization, and other NLP pipelines entirely client-side via WASM or WebGPU, with inference-only support (no fine-tuning) — Source: Hugging Face Transformers.js docs/blog, Feb 9 2026 (v4 release), accessed 2026-10-28, confidence: high, class: tooling/landscape
- Transformers.js v4 (Feb 2026) migrated its build to esbuild (build time 2s→200ms), cut average bundle size ~10%, made the default `transformers.web.js` export 53% smaller, and ships a standalone zero-dependency tokenizer at 8.8kB gzipped — Source: Hugging Face blog "Transformers.js v4", 2026-02-09, accessed 2026-10-28, confidence: high, class: implementation effort / bundle size
- For classification-sized models, quantized int8 ONNX checkpoints are realistically small: Xenova/all-MiniLM-L6-v2 ≈23MB; a quantized DistilBERT dropped from 256MB (fp32) to 64MB (int8) — these sizes (tens of MB) are the realistic class of model for a "tag/prioritize this task" classifier, as opposed to generative LLMs which run 2–4GB+ — Source: Hugging Face model hub (Xenova/transformers.js quantized repo) + dev.to "What I Learned Quantizing DistilBERT to ONNX for Browser Inference" (fuxionixt), dated ~Sept 2025, accessed 2026-10-28, confidence: medium, class: model size
- Real measured numbers from that DistilBERT build: int8 quantization cut size 4x (256MB→64MB) with only a 0.12-point accuracy loss; browser (WASM) inference latency was ~58ms per call in Chrome — fast enough for "suggest on capture" UX — but the author explicitly notes "Safari currently fails to load it" — Source: dev.to, fuxionixt, n.d. (~Sept 2025), accessed 2026-10-28, confidence: medium, class: inference latency / browser compatibility
- WebLLM (generative LLM in browser via WebGPU) numbers are only relevant if attempting short free-text generation rather than classification: first-time download of an 8B model (Llama-3-8B, 4.2GB) takes ~6 minutes on 100Mbps; a 3.8B model (Phi-3) ~3 minutes; cached reload is much faster (~4.5s–27s depending on model); decode throughput ~41 tok/s for Llama-3.1-8B (≈80% of native speed) — these sizes/times are impractical for a lightweight to-do-app feature and point toward classification-only use of the in-browser-AI approach for v1 — Source: WebLLM paper (arXiv 2412.15803) and dev.to "Run an LLM in the browser: WebGPU did 63 tokens/s" (mattbusel), n.d. ~2025, accessed 2026-10-28, confidence: medium, class: load time / inference latency
- Safari/WebKit only gained WebGPU support in Safari 26 (shipped Sept 2025, covering macOS Tahoe 26 / iOS 26 / iPadOS 26) — before that, Safari/iOS had no WebGPU, meaning ONNX Runtime Web / transformers.js on iOS had to fall back to WASM-only CPU execution — Source: web.dev blog "WebGPU is now supported in major browsers" + AppDeveloperMagazine "WebGPU in iOS 26", 2025-09, accessed 2026-10-28, confidence: high, class: browser compatibility
- A currently open, actively-discussed defect: ONNX Runtime Web's WebGPU/JSEP execution mode on Safari/WebKit 26 causes severe CPU (400%+) and memory (1GB→14GB+) blowups leading to tab crashes on iOS; reported ~Jan 2026 (issue #26827) and confirmed still present in ONNX Runtime 1.30.0 via a follow-up issue (#33516) as of the search date — multiple independent app repos (badugi-app, Tab-Translator-Pro, BirdBox, mtg-playin-scanner) worked around it by forcing CPU-only WASM execution and/or pinning ONNX Runtime to 1.23.2 rather than using WebGPU/JSEP on Safari — Source: microsoft/onnxruntime GitHub issues #26827 and #33516, reported ~Jan 2026, accessed 2026-10-28, confidence: high, class: browser compatibility (iOS/Safari) — an evolving, still-open bug thread; treat as current but watch for fixes.
- iOS Safari imposes a practical tab memory ceiling of roughly <500MB, and WebGPU's own spec defaults only guarantee 256MB max buffer size / 128MB max storage-buffer binding (can be raised, up to ~1GB on some devices); Safari's Metal backend per-buffer limits range from 256MB (older iPhones) to 993MB (iPad Pro) — this constrains model choice on mobile regardless of GPU acceleration, but is not a binding constraint for classification models in the 20–65MB range — Source: note.com "The Era of LLMs Running in the Browser" and tianpan.co "Browser-Native LLM Inference," n.d. 2025/2026, accessed 2026-10-28, confidence: medium, class: device/memory constraints
- Production integration pitfalls reported for shipping transformers.js: large ONNX model downloads stall page load if not lazy-loaded (recommendation: lazy-load the model after initial render with a loading state, since even a 50MB download on first visit is a UX problem); WASM execution competes with the main thread / rendering loop; standard bundler configs (webpack/vite) don't handle binary ONNX/WASM assets out of the box — Source: SitePoint "Optimizing Transformers.js for Production Web Apps" (search-snippet derived; direct fetch returned HTTP 403), n.d. 2025, accessed 2026-10-28, confidence: low-medium (not independently verified by full-page fetch), class: implementation effort
- Additional concrete pitfalls from the DistilBERT browser build: a token_type_ids signature mismatch broke raw inference sessions; the quantization dtype matters for the browser specifically — QUInt8 (not QInt8) is required for browser compatibility; transformers.js expects a specific `onnx/` subfolder directory layout for model files; and quantization, while shrinking file size, actually increased inference latency on Apple Silicon in this author's testing (a non-obvious size/speed tradeoff) — Source: dev.to, fuxionixt, n.d. ~Sept 2025, accessed 2026-10-28, confidence: medium, class: implementation effort
- Cost and privacy are architectural guarantees of this approach rather than separately-measured facts: because inference runs via WASM/WebGPU entirely inside the browser process with the model cached locally (via browser HTTP cache / service worker after first download), there is no per-call API cost and no network round-trip carrying task text off-device. Hugging Face's own materials describe transformers.js models as running "100% locally in the browser." The real costs are non-monetary: initial download weight (23MB–64MB range for realistic classification models, one-time, cacheable), bundle-size overhead in the shipped app, and CPU/battery draw during inference — Source: Hugging Face Transformers.js blog/docs, 2026-02-09, accessed 2026-10-28, confidence: high, class: cost / privacy

### Leads
- The Safari/WebKit 26 ONNX Runtime WebGPU(JSEP) memory-leak bug (#26827/#33516) is a load-bearing compatibility risk specifically for this candidate on iOS/iPadOS — still open as of the most recent follow-up found (version 1.30.0). The documented workaround (force `executionProviders: ['wasm']`, avoid WebGPU/JSEP, possibly pin an ONNX Runtime version) should be treated as a required mitigation, not optional, if targeting iPhone/iPad.
- The "Safari currently fails to load it" claim from the DistilBERT quantization blog post is lower-confidence/possibly stale — unclear whether a transformers.js/ONNX Runtime version issue since fixed, or the same root cause as the #26827 Safari/WebKit 26 bug.
- WebLLM numbers found were all for generative LLMs (1B–8B params); no direct benchmark was found for WebLLM running a small classification-sized model — transformers.js + ONNX quantized encoder models (DistilBERT/MiniLM-class) looks like the better-fit, lighter-weight path versus WebLLM for this use case, but this is an inference, not a head-to-head source.
- The SitePoint production-optimization article could not be fetched directly (403); its lazy-loading/bundler claims rest on a search-snippet summary, not the full page.

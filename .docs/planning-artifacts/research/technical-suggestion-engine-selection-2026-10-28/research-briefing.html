Executive summary

Recommendation: rule-based classifier as the permanent fallback, with an optional Claude API call (Haiku tier) layered on top as the primary path when a key is configured. OpenAI's API is an equally-capable, slightly better-evidenced-on-latency runner-up — pick whichever key the student already has. The in-browser local-model option is not recommended for v1: this round turned up a concrete, currently-open, dated bug (ONNX Runtime Web's WebGPU execution mode crashing tabs on Safari/iOS, still unresolved as of the most recent follow-up found) that makes it the riskiest of the three AI options, not just the most complex in the abstract.

The real choice is still not "pick one of four" — the rule-based engine ships either way as the mandatory no-key fallback. A concrete, reusable version of that fallback surfaced this round: a real open-source task-triage project (fazal305/nightbeacon) documents that its keyword classifier "can misjudge priority on ambiguous text," and proposes escalating only low-confidence/ambiguous cases to a small LLM rather than replacing the rule engine outright [3] — close to the exact architecture recommended here.

Two genuine disputes surfaced in this round's sources and are reported honestly rather than averaged: the size of the rule-based-vs-ML accuracy gap [1][7], and Claude Haiku 5.5's short-call latency, where sources disagree by roughly 10x [13]. Both cloud APIs share one confirmed, actionable mechanism behind latency swings like this: a "reasoning effort" setting that must be pinned to its lowest value for a short classification call [13][21].

Biggest caveat: free-trial credit amounts, OpenAI's exact current cheapest model name, and whether the Safari/WebKit ONNX bug has since been patched are all reported only by secondary sources or are actively churning as of this research date — see Open Questions. None of this changes the recommendation; it changes what to re-verify at implementation time.

Evidence per candidate

Candidate 1 — Rule-based / keyword classifier only

  • Real, working precedent exists: a Flask task-triage app classifies into 5 categories/4 priority levels offline with no API key, and its own README flags "LLM-based classification" as future work — evidence of a known ceiling from someone who lived with the rule-based version high [2]. A second project documents the same ceiling directly: "can misjudge priority on ambiguous text" high [3].
  • A concrete, reusable rule design was found: tokenize/lowercase, weight two-word phrases at 3 and single tokens at 1, urgency/deferral keyword maps for priority, 0.35 confidence floor, ties resolve to "other" medium (spec only) [4].
  • Accuracy gap vs. ML is disputed. One unverified source cites 69.4% vs. 87.5% disputed [1]; a peer-reviewed microtext study instead found rule-based and ML "perform well on different parts" of a dataset medium [7] — a narrower, more task-dependent gap than one headline number implies.
  • JS/TS landscape: compromise (rule-based parsing, not classification), natural (ships trainable ML classifiers, not rule-based by default), wink-nlp (525,000+ tokens/sec, supports custom rule-based entities) medium [5][9].
  • Zero marginal cost, near-instant latency, no data ever leaves the device — architectural certainties, corroborated by real "runs offline, no API key" precedent high [2][10].

Candidate 2 — Rule-based + optional Claude API

  • Claude Haiku 5.5 (released 2026-10-07, ~90% price cut vs. 4.5): $0.10/MTok input, $0.50/MTok output, confirmed on Anthropic's live pricing page high [11][12] → roughly $0.00005–0.0001 per call.
  • Latency is genuinely disputed, not just uncertain. One tracker shows ~0.7–1.0s; artificialanalysis.ai's own Haiku 5.5 pages show 9.6–13.4s "time to first answer token" at low/medium reasoning effort disputed [13]. Should be empirically timed with a real key before assuming either number.
  • Integration confirmed directly on Anthropic's docs: Messages API output_config.json_schema, x-api-key auth, SDK .parse() helper high [16].
  • Privacy — strongest-sourced claim in this report: fetched directly from Anthropic's own privacy center (policy dated 2026-08-18) — API input/output not used for training by default, 30-day auto-deletion unless opted in high [17].
  • Free credit (~$5) and rate limits only reported by third-party aggregators, not confirmed on an Anthropic page low-medium [14][15].

Candidate 3 — Rule-based + optional OpenAI API

  • GPT-5-nano: $0.05/MTok input, $0.40/MTok output, confirmed on OpenAI's live pricing page and cross-checked against an independent calculator high [19][20] → roughly $0.00003–0.00006 per call, cheapest of the two APIs.
  • Latency mechanism confirmed more cleanly than Claude's: "minimal" effort ~0.8s TTFT; "medium/high" effort balloons to 37–118s on the same model — a consistent evidence trail medium [21].
  • Integration confirmed directly on OpenAI's docs: Responses API Structured Outputs (strict:true JSON schema), Bearer auth, SDK .parse() high [24].
  • Privacy confirmed directly on OpenAI's data-usage guide (policy effective 2023-03-01) — not used for training by default high [22].
  • Free tier and current cheapest-model name are both actively churning — newer model names already appearing in OpenAI's own example docs low-medium [19][25][26].

Candidate 4 — Rule-based + in-browser local model

  • Realistic classification models are small and well-documented: MiniLM ≈23MB, quantized DistilBERT 64MB (0.12-pt accuracy loss) medium [27][28]; measured ~58ms WASM latency in Chrome — fast enough for "suggest on capture" medium [28].
  • Decisive new finding this round: a concrete, dated, still-open browser bug. ONNX Runtime Web's WebGPU/JSEP mode causes severe CPU/memory blowups and tab crashes on Safari/iOS — reported ~Jan 2026, confirmed still open in v1.30.0. Workaround requires forcing WASM-only execution on Safari high [32]. This is a specific, named, currently-unresolved defect, not an abstract complexity concern.
  • Generative use (the "summary" feature) is a worse fit — WebLLM-class models are 4.2GB+ and take minutes to download; realistic use here is classification-only medium [30].
  • Cost/privacy architecturally strong (zero per-call cost, no data leaves device once cached) high [27], but real non-monetary costs: bundle size, mobile memory ceilings, bundler/asset-pipeline pitfalls medium [29][33][34].

Cross-dimension insights

  • The local-model candidate's risk profile sharpened this round from "abstractly complex" to "concretely broken on one major platform, right now" — a still-open, dated GitHub issue thread is stronger evidence than general cross-browser-complexity concerns alone.
  • Both cloud APIs share the same latency trap, but the evidence for it is asymmetric. OpenAI's reasoning-effort mechanism is confirmed with a clean, consistent number set; Claude's own evidence trail is contradictory in this round. Claude is still picked on pricing/privacy/primary-source strength, but its latency should be empirically timed before assuming a UX without a loading state.
  • Rule-based-alone still isn't competing on the same axis as the other three. It wins cleanly on cost/latency/privacy/simplicity, and real precedent now confirms rule-based engines are shipped standalone in similar small apps — but whether that alone satisfies the course's "practical AI use" grading weight is a judgment this research can't resolve with web evidence.

Verdict

Pick

Rule-based (fallback, always) + Claude API (optional primary)

Full LLM-grade quality, near-zero cost, strongest-sourced privacy policy of the four. Latency should be empirically timed before shipping — sources disagree.

Named runner-up

Rule-based + OpenAI API

Tied on cost/privacy; this round's latency evidence for it is cleaner and more internally consistent than Claude's. Wins if that matters more to you than Claude's other strengths.

Not recommended for v1

Rule-based + local in-browser model

Best privacy/cost on paper, but a concrete, dated, still-open Safari/iOS crash bug in the exact runtime layer it depends on. Re-check if revisited in Vision.

Not recommended alone

Rule-based only

Wins the matrix on the five scored criteria, and real precedent confirms it's shippable standalone — but risks not clearing the course's "practical AI use" grading weight by itself. Ships either way as the fallback.

Strongest argument against the pick

The Claude latency dispute itself. If Haiku 5.5's slower, reasoning-effort-engaged numbers (9.6–13.4s) turn out to be what a real implementation gets by default, Claude would feel meaningfully slower than OpenAI's more consistently sub-second nano tier for the same task. Testable in under an hour with a real API key — do this before finalizing the provider choice in the PRD.

Cheapest reversibility hedge

Build the suggestion engine behind one interface — a function returning {tags, priority, summary} — with the rule-based classifier and the chosen API call as interchangeable implementations. Already required by the mandatory-fallback architecture, and it matches the real hybrid pattern found this round (escalate only ambiguous cases to an LLM, per [3]).

Feeds: an input to the PRD's resolution of its own "Open Decision Point," and an architecture constraint (the swappable-provider interface) once architecture work starts.

Open questions

  • Empirically time a real Claude Haiku 5.5 call with reasoning effort pinned to minimal before trusting either latency number — the sources disagree and this affects whether a loading-state UX is needed.
  • Exact current free-trial credit amounts for both providers are only reported secondarily. Check both providers' billing/dashboard pages directly before writing grader/setup instructions.
  • OpenAI's exact current cheapest model name is actively churning — newer names already appear in OpenAI's own example docs. Re-check before hard-coding gpt-5-nano.
  • Whether the Safari/WebKit ONNX Runtime Web memory bug (#26827/#33516) has been patched should be re-checked if the local-model path is ever revisited.
  • No direct benchmark exists for rule-based vs. AI accuracy on todo-task tagging specifically — the two sources found actively disagree on the gap's size. The brief's own 10–15 example-task test fixture is the right way to generate this evidence locally.
  • Red-team pass did not run (off by default at normal validation). Re-run at high validation for a dedicated adversarial pass.
